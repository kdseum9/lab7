1. Создай и подключи класс команды - Command classes

Для новой команды создай <НазваниеКоманды>Command.java в src/main/java/org/example/server/command/, объявив пакет org.example.server.command.
Унаследуй класс от AbstractCommand и переопредели Response execute(Request request, CollectionManager collectionManager) с @Override.
При изменении существующей команды измени её класс вместо создания второго обработчика того же имени.
Реализуй в команде последовательность выполнения: получение параметров, вызов проверок и менеджеров, формирование результата. Операции с коллекцией и БД поручай соответствующим менеджерам.
Зарегистрируй новую команду в конструкторе CommandManager: commands.put("имя_команды", new НазваниеКомандыCommand()). Имя должно совпадать с Request.getCommandName().
Добавь название, формат ввода и назначение новой команды в справку HelpCommand.
Не реализуй выполнение пользовательской команды непосредственно в Client или Server.

2. Организуй доступ к БД - Database access

Если команда обращается к PostgreSQL, найди подходящий метод в DataBaseManager и проверь его параметры, возвращаемое значение и условия отказа.
Если нужной операции нет, добавь её в DataBaseManager. Размещай SQL, создание соединений, JDBC-вызовы и обработку результатов запросов только там.
Для операций над личными данными используй пользователя из запроса после серверной проверки аутентификации и проверяй принадлежность данных. Не считай переданный клиентом логин или ownerId самостоятельным подтверждением права доступа.
Для изменения хранимого билета сначала проверь входные данные и права. Обновляй состояние коллекции только после подтверждённого успеха операции в БД.
Не создавай второй механизм подключения к PostgreSQL. Не добавляй SQL, Connection, PreparedStatement, Statement или ResultSet в команды, Client и Server.




3. Проверь входные данные - Validation

На серверной стороне проверь наличие Request.args и ожидаемое число аргументов до обращения к элементам массива. Для команды с объектом проверь наличие Request.ticket.
Для полей моделей используй подходящие методы TicketValidator, CoordinatesValidator и VenueValidator из org.example.server.manager. Например, цену проверяй через TicketValidator.priceIsOk(...).
Проверь фактические ограничения выбранного метода. Если задача требует дополнительной проверки поля модели, добавь её в соответствующий валидатор вместо копирования правил в команду.
Учитывай результат проверки: методы, возвращающие boolean, должны приводить к отказу при false; исключения валидатора должны прерывать выполнение операции
Выполни проверки до записи в БД и изменения коллекции. Проверка на клиенте не заменяет серверную проверку.
Не дублируй существующие правила проверки моделей в классах команд.

4. Обработай ошибки - Error-handling

Изучи исключения в org.example.common.exceptions до создания нового типа.
Используй WrongArgumentException для некорректных аргументов и NoElementException для отсутствующего запрошенного элемента, если они соответствуют ситуации. Пустой результат поиска или экспорта сам по себе не означает отсутствие запрошенного элемента.
Сохраняй сигнатуру AbstractCommand.execute(). Обработай WrongArgumentException внутри команды и преобразуй его в Response, либо обработай его на уже существующей подходящей границе. Не добавляй несовместимое checked-исключение в переопределение.
Не заменяй подходящее исключение произвольной строкой, обходящей механизм исключений. Сообщение в Response допустимо как результат обработки исключения, отправляемый клиенту.
Если менеджер сообщает об отказе через false, null или другое документированное значение, проверь этот результат. Не продолжай изменение коллекции после отказа БД.
Для ошибок, которым не соответствует существующее исключение, используй подходящую обработку на границе команды; новый тип вводи только при реальной необходимости.
Возвращай результат команды через Response, а не только печатай его в консоль сервера.

5. Передай параметры команды - Client-Server protocol

Передавай серверные параметры через существующий Request: простые значения - через args, билет - через ticket, данные аутентификации - через login и password.
Согласуй порядок аргументов на клиенте, в скрипте и на сервере. Имя команды хранится в commandName; первый параметр новой команды размещай в args[0].
Если требуется ввод, добавь соответствующий случай в Client.handleCommand(). Используй существующие конструкторы Request и путь отправки Client.sendRequest(), который заполняет данные аутентификации.
Добавь эквивалентное формирование запроса в ScriptExecutor.executeScript(). В этом проекте дополнительные значения для существующих команд читаются с последующих строк файла. Проверь конец файла до использования прочитанной строки.
Для команды без серверных параметров используй существующее формирование запроса с пустым массивом аргументов и null вместо билета, если оно подходит задаче.
Если клиент выполняет дополнительное действие с ответом, обеспечь это действие и при интерактивном вводе, и при выполнении скрипта.
Сохрани Java-сериализацию Request и существующие способы отправки и получения данных. Если действительно необходимо расширить Request, согласованно обнови создание и чтение запроса на обеих сторонах.
Не вводи параллельный протокол и не передавай параметры команды отдельными сетевыми сообщениями в обход Request.

6. Выполни операции с коллекцией - Collection access

Найди нужную операцию в CollectionManager и используй её. Если подходящего метода нет, реализуй его в CollectionManager и вызови из команды.
Размещай поиск, фильтрацию и изменение основной коллекции в методах менеджера; не копируй эту логику в несколько команд.
Не удаляй и не добавляй элементы в результат getCollection() в расчёте на изменение состояния приложения: метод возвращает new LinkedHashSet<>(collection).
Учитывай, что копия набора поверхностная: объекты Ticket остаются общими. Не меняй поля полученных билетов из команды, обходя менеджер.
При обновлении билета учитывай, что его изменяемые поля участвуют в equals() и hashCode(). В методе менеджера удаляй старый элемент из набора до изменения таких полей либо заменяй его корректно подготовленным объектом, сохраняя идентичность билета
Сохрани применяемую в менеджере синхронизацию при доступе к коллекции. Не запрашивай пользовательский ввод из серверного менеджера

7. Проверь размещение кода - Layer separation

Оставь в Client пользовательский ввод, формирование и отправку запроса, получение и отображение ответа, а также локальные действия, прямо требуемые задачей.
Оставь в ScriptExecutor чтение скрипта и формирование соответствующих запросов, без серверной логики работы с билетами.
Оставь в Server сетевое взаимодействие и существующую обработку/диспетчеризацию запросов. Обычную новую команду выполняй через CommandManager; не добавляй для неё отдельную бизнес-ветку в Server.
Размести координацию команды в её классе, операции с коллекцией - в CollectionManager, работу с PostgreSQL - в DataBaseManager, проверки моделей - в валидаторах.
Не переноси ответственность одного слоя в другой и не переписывай несвязанные команды в рамках задачи.
